# Grasshopper용 진단 도구 (제안)

> 검토용 제안 문서입니다. 아직 정한 것은 없습니다. [vim에서 더 가져올 것](vim-ideas.md)의 3번(진단으로 점프, hover)을 확장한 내용입니다.

Grasshopper에도 LSP 비슷한 것은 있습니다. 입력이 부족하면 주황색, 에러가 나면 빨간색으로 표시되고 최소한의 메시지도 있습니다. 문제는 그 성능이 빈약해서, **무엇 때문에 어떤 문제가 생겼는지** 디버깅하기 어렵다는 점입니다. 그래서 LSP 프로토콜을 붙이는 게 아니라, **Grasshopper 안에서 LSP가 하는 일(진단, 원인 추적, hover, 빠른 수정)을 하는 분석기**를 제안합니다. 키보드로 진단 사이를 뛰어다니는 경험은 hjkl 이동, 자동 정렬과 자연스럽게 이어집니다.

## Grasshopper 디버깅이 어려운 이유

1. **메시지가 그 자리의 증상만 말합니다.** "Data conversion failed from Text to Number"는 어디서 잘못된 텍스트가 들어왔는지 알려주지 않습니다.
2. **경고가 연쇄됩니다.** 상류 하나가 실패하면 하류가 줄줄이 주황색이 됩니다. 진짜 원인 하나가 경고 스무 개에 묻힙니다.
3. **가장 큰 문제는 에러가 안 나는 경우입니다.** 데이터 트리 구조가 어긋나면(가지 수가 다름, flatten을 빠뜨림 등) Grasshopper는 longest list 규칙으로 조용히 짝을 맞춥니다. 결과는 틀렸는데 아무 색도 안 뜹니다.
4. **null과 빈 가지가 소리 없이 퍼집니다.** 어디서 처음 생겼는지 추적할 방법이 없습니다.

## 할 수 있는 것 (가치가 큰 순서)

### 1. 데이터 짝 맞춤 검사 (3번 문제)

계산이 끝난 뒤 각 컴포넌트 입력들의 트리 구조를 비교합니다.

- "입력 A는 가지 10개, 입력 B는 3개 → B의 마지막 가지가 7번 반복 사용됨"
- "A는 항목 100개, B는 1개 → B가 100번 재사용됨 (의도한 것이면 무시)"
- 에러가 아니라 **힌트 등급**으로 보여줍니다. 의도한 경우도 많기 때문입니다.

### 2. 근본 원인 묶기 (2번 문제)

경고·에러가 난 컴포넌트에서 상류로 거슬러 올라가 **가장 먼저 문제가 생긴 곳**을 찾습니다. 그리고 "이 경고 12개는 모두 X 때문"으로 묶어서 보여줍니다. `]e` / `[e`는 원인으로만 이동합니다.

### 3. 데이터 모양 보기 (hover `K`)

선택한 파라미터의 경로 수, 가지별 항목 수, null 개수, 타입을 보여줍니다. 입력과 출력의 모양을 나란히 보여주면, 이 컴포넌트가 데이터를 어떻게 바꿨는지 한눈에 보입니다.

### 4. null·빈 데이터의 출처 추적 (4번 문제)

하류에서 null을 발견하면 처음 null이 생긴 컴포넌트까지 거슬러 올라갑니다.

### 5. 빠른 수정 (code action)

1번 진단에 "B를 graft하면 짝이 맞습니다" 같은 제안을 붙입니다. 이미 있는 데이터 연산자(`f` `g` `s` `r`)로 키 한 번에 적용할 수 있습니다.

### 6. 기타

- inlay hint: 와이어 위에 트리 모양 `{3;10}`을 작게 표시
- 프로파일링: 느린 컴포넌트 표시

## 기술적으로 가능한가

가능합니다. 필요한 정보는 모두 Grasshopper API로 직접 읽을 수 있습니다.

| 필요한 것 | API |
|---|---|
| 런타임 메시지 | `IGH_ActiveObject.RuntimeMessages(level)` |
| 계산된 데이터 | `IGH_Param.VolatileData` (경로, 가지, 항목 수, 타입) |
| 계산 완료 시점 | `GH_Document.SolutionEnd` 이벤트 |
| 소요 시간 | 컴포넌트별 처리 시간 |

구조는 지금과 같게 갑니다. Engine은 계산이 끝날 때 데이터의 **모양만** 요약해서(실제 지오메트리는 복사하지 않음) Core로 넘기고, 진단 규칙은 Core에서 순수 로직으로 돌립니다. 그래서 단위 테스트를 할 수 있습니다.

## 주의할 점

- **계산이 끝난 뒤에만 분석할 수 있습니다.** 정적 분석이 아니라 실제 결과를 보는 방식입니다. 대신 실제 데이터를 보므로 정확합니다.
- **계산을 느리게 하면 안 됩니다.** 개수만 세면 가볍지만, 큰 정의에서는 바뀐 부분만 다시 분석하는 장치가 필요할 수 있습니다.
- **짝 맞춤 검사는 오탐이 생길 수 있습니다.** 슬라이더 하나를 100개 항목에 쓰는 건 정상입니다. 처음에는 "의도가 애매한 경우"만 좁게 잡고, 무시 표시를 할 수 있게 해야 합니다.
- **범위가 커집니다.** 처음에는 Vimhopper 안의 진단 모듈로 시작하고, Core를 분리해 두면 나중에 별도 플러그인으로 떼어낼 수 있습니다.

## 시작한다면

작게 시작해서 효과를 확인하는 순서를 추천합니다.

1. 계산이 끝날 때 메시지와 데이터 모양 수집
2. 근본 원인 묶기와 `]e` / `[e` 이동
3. `K`로 데이터 모양 보기
4. 데이터 짝 맞춤 검사와 빠른 수정

1~3은 Grasshopper가 이미 주는 정보를 잘 정리하는 수준이라 위험이 적습니다. 4가 진짜 차별점이지만, 무엇을 의심스러운 짝 맞춤으로 볼지 규칙을 설계하는 데 시간이 필요합니다.
