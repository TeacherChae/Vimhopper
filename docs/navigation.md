# 이동 (hjkl)

구현: `src/Vimhopper.Core/GraphNavigator.cs`. 키 목록은 [키맵](keymap.md#이동)을 참고하세요.

## 문제

Grasshopper의 연결은 트리가 아니라 방향 그래프(DAG)입니다. 한 컴포넌트가 **부모도 여러 개, 자식도 여러 개** 가질 수 있습니다. 첫 구현(`TreeNavigator`, 제거됨)은 "어느 방향으로 건너왔는가"라는 이동 기록으로 이 모호함을 풀었는데, 그러면 **같은 컴포넌트에서 같은 키를 눌러도 직전 경로에 따라 결과가 달라져** 예측하기 어려웠습니다.

## 결정: 자동 정렬과 같은 기준으로

이동 기록과 무관하게 **현재 선택된 객체만 보고** 결정합니다. 기준은 [자동 정렬](formatting.md)과 같아서, **정렬된 화면에서는 hjkl이 그대로 화면상 좌·하·상·우가 됩니다.** 정렬하지 않은 화면에서도 같은 규칙으로 동작합니다 (층은 좌표가 아니라 연결 구조만으로 정해지므로).

| 키 | 동작 | 정렬된 화면에서 |
|---|---|---|
| `h` | 맨 위 입력의 출처로 | 수평 와이어를 따라 왼쪽 |
| `l` | 내 출력을 맨 위 입력으로 받는 자식 중 첫 번째. 없으면 자식 중 첫 번째 | 수평 와이어를 따라 오른쪽 |
| `j` / `k` | 같은 층(자동 정렬의 열) 안 다음 / 이전 객체 | 같은 세로줄에서 아래 / 위 |

- **"맨 위 입력"**은 연결된 입력 중 번호가 가장 작은 것입니다. 정렬이 이 와이어를 수평으로 맞추므로 `h`/`l`이 수평 와이어를 따라가게 됩니다. 순서 기준이 파라미터 번호이므로 `o{n}`/`i{n}`의 번호와도 일관됩니다.
- **자식 순서**는 출력 번호, 같은 출력 안에서는 화면 위→아래입니다.
- **`{n}h` / `{n}l`**: n번 입력의 출처 / n번 출력을 받는 자식으로. `h`만으로는 맨 위가 아닌 부모로 갈 수 없기 때문입니다 (예: 아래 예제에서 `Domain`의 입력 B 출처인 `w/2`는 `Neg`와 다른 층이라 `j`/`k`로도 닿지 않음). 입력 번호는 Vim 모드에서 화면에 표시됩니다. `{n}j`/`{n}k`는 vim처럼 n칸 이동입니다.
- **`j`/`k`는 덩어리 경계를 넘어갑니다.** 덩어리끼리는 와이어로 이어져 있지 않으므로, 넘어갈 때는 다음 덩어리(`g=`가 쌓는 순서)에서 **같은 깊이(같은 층 번호)**의 객체로 갑니다. 정렬된 화면이라면 같은 세로줄을 따라 계속 내려가는 것과 같습니다.
- **되돌아가기**: `l`은 "나를 맨 위 입력으로 받는 자식"을 우선하므로, `l`로 간 곳에서 `h`를 누르면 거의 항상 원래 자리로 돌아옵니다. 그렇지 않은 경우도 원래 객체가 같은 층에 있으면 `j`/`k`로 갈 수 있으므로, 별도의 이동 기록 키(`Ctrl+o`/`Ctrl+i`)는 지금은 두지 않습니다.

```
 층1        층2        층3
[w/2]──┬──[Neg]────[Domain]   Domain에서 h → Neg,  1h → w/2
       └─────────────┘         w/2에서 l → Neg (Neg의 맨 위 입력이 w/2)
```

## Relay

- Relay도 일반 객체처럼 멈춥니다. 한 Relay에서 여러 갈래가 나갈 수 있으므로 건너뛰지 않습니다.
- **층**은 정렬처럼 Relay를 풀고 계산합니다. Relay를 일반 객체로 세면 `A → R → B`에서 B가 한 층 밀려 정렬된 화면의 열과 어긋나기 때문입니다.
- Relay 자체는 입력값(슬라이더 등)과 같은 규칙으로, 받는 객체 중 가장 왼쪽 층의 바로 앞 층에 넣습니다. 정렬도 Relay를 대부분 받는 쪽 바로 앞에 놓으므로 화면과 거의 일치합니다.

## 정렬과 어긋나지 않게

층 계산은 정렬 코드(`CanvasLayout.Layers`)를 그대로 씁니다. 그래서 두 기능의 열 번호가 어긋나지 않습니다.
