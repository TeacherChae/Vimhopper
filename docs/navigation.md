# 이동 (hjkl)

구현: `src/Vimhopper.Core/GraphNavigator.cs`. 키 목록은 [키맵](keymap.md#이동)을 참고하세요.

## 문제

Grasshopper의 연결은 트리가 아니라 방향 그래프(DAG)입니다. 한 컴포넌트가 **부모도 여러 개, 자식도 여러 개** 가질 수 있습니다. 첫 구현(`TreeNavigator`, 제거됨)은 "어느 방향으로 건너왔는가"라는 이동 기록으로 이 모호함을 풀었는데, 그러면 **같은 컴포넌트에서 같은 키를 눌러도 직전 경로에 따라 결과가 달라져** 예측하기 어려웠습니다.

## 결정: 자동 정렬과 같은 기준으로

이동 기록과 무관하게 **현재 선택된 객체만 보고** 결정합니다. 기준은 [자동 정렬](formatting.md)과 같아서, **정렬된 화면에서는 hjkl이 그대로 화면상 좌·하·상·우가 됩니다.** 정렬하지 않은 화면에서도 같은 규칙으로 동작합니다 (층은 좌표가 아니라 연결 구조만으로 정해지므로).

| 키 | 동작 | 정렬된 화면에서 |
|---|---|---|
| `h` | 맨 위 입력의 출처로 | 수평 와이어를 따라 왼쪽 |
| `l` | 내 출력을 맨 위 입력으로 받는 자식 중 첫 번째. 없으면 자식 중 첫 번째 | 수평 와이어를 따라 오른쪽 |
| `j` / `k` | 같은 층(자동 정렬의 열) 안 다음 / 이전 객체 | 같은 세로줄에서 아래 / 위 |

- **"맨 위 입력"**은 연결된 입력 중 번호가 가장 작은 것입니다. 정렬이 이 와이어를 수평으로 맞추므로 `h`/`l`이 수평 와이어를 따라가게 됩니다. 순서 기준이 파라미터 번호이므로 `o{n}`/`i{n}`의 번호와도 일관됩니다.
- **자식 순서**는 출력 번호, 같은 출력 안에서는 화면 위→아래입니다.
- **`{n}h` / `{n}l`**: n번 입력의 출처 / n번 출력을 받는 자식으로. `h`만으로는 맨 위가 아닌 부모로 갈 수 없기 때문입니다 (예: 아래 예제에서 `Domain`의 입력 B 출처인 `w/2`는 `Neg`와 다른 층이라 `j`/`k`로도 닿지 않음). 입력 번호는 Vim 모드에서 화면에 표시됩니다. `{n}j`/`{n}k`는 vim처럼 n칸 이동입니다.
- **`j`/`k`는 덩어리 경계를 넘어갑니다.** 덩어리끼리는 와이어로 이어져 있지 않으므로, 넘어갈 때는 다음 덩어리(`g=`가 쌓는 순서)에서 **같은 깊이(같은 층 번호)**의 객체로 갑니다. 정렬된 화면이라면 같은 세로줄을 따라 계속 내려가는 것과 같습니다.
- **되돌아가기**: `l`은 "나를 맨 위 입력으로 받는 자식"을 우선하므로, `l`로 간 곳에서 `h`를 누르면 거의 항상 원래 자리로 돌아옵니다. 그렇지 않은 경우도 원래 객체가 같은 층에 있으면 `j`/`k`로 갈 수 있으므로, 별도의 이동 기록 키(`Ctrl+o`/`Ctrl+i`)는 지금은 두지 않습니다.

```
 층1        층2        층3
[w/2]──┬──[Neg]────[Domain]   Domain에서 h → Neg,  1h → w/2
       └─────────────┘         w/2에서 l → Neg (Neg의 맨 위 입력이 w/2)
```

## Relay

- Relay도 일반 객체처럼 멈춥니다. 한 Relay에서 여러 갈래가 나갈 수 있으므로 건너뛰지 않습니다.
- **층**은 정렬처럼 Relay를 풀고 계산합니다. Relay를 일반 객체로 세면 `A → R → B`에서 B가 한 층 밀려 정렬된 화면의 열과 어긋나기 때문입니다.
- Relay 자체는 입력값(슬라이더 등)과 같은 규칙으로, 받는 객체 중 가장 왼쪽 층의 바로 앞 층에 넣습니다. 정렬도 Relay를 대부분 받는 쪽 바로 앞에 놓으므로 화면과 거의 일치합니다.

## 정렬과 어긋나지 않게

층 계산은 정렬 코드(`CanvasLayout.Layers`)를 그대로 씁니다. 그래서 두 기능의 열 번호가 어긋나지 않습니다.

## 미해결: `부모 없음` / `자식 없음`이 자주 나옴

> 조사만 하고 아직 고치지 않았습니다. 비주얼 모드에서 `hjkl`로 범위를 넓히다 보면 이 메시지가 자주 나온다는 사용 소감에서 시작했습니다.

`h`/`l`은 `GraphNavigator.Parent` / `Child`가 null을 돌려줄 때 실패합니다 (`VimController.Move`에서 메시지 표시). 코드 기준으로 그런 경우는 아래와 같습니다.

### 구조상 정말 없는 경우 (규칙대로 동작하지만 막힘)

1. **입력값에서 `h`**: 슬라이더, 패널, Value List처럼 입력 그립이 없거나 입력이 연결되지 않은 객체. 정렬된 화면의 맨 왼쪽 열입니다.
2. **입력이 하나도 연결되지 않은 컴포넌트에서 `h`**: 모든 입력이 기본값이나 내부값인 경우. 정렬에서는 0층이라 역시 맨 왼쪽에 놓입니다.
3. **끝 객체에서 `l`**: 출력이 아무 데도 연결되지 않은 객체. 결과 확인용 패널, Preview, 마지막 컴포넌트 등입니다.
4. **덩어리 경계**: `h`/`l`은 와이어만 따라가므로 옆에 있는 다른 덩어리로 건너가지 못합니다. `j`/`k`는 덩어리 경계를 넘어가므로 비대칭입니다.

### 와이어가 아닌 연결 (확인 필요)

5. **특수 객체**: Galapagos, Timer처럼 `Sources`/`Recipients`가 아닌 방식으로 이어지는 객체는 `VimController.Params`가 빈 목록을 돌려주므로 그래프에서 고립됩니다. 각 객체가 `IGH_ActiveObject`인지, 실제로 어떻게 보이는지는 Rhino에서 확인하지 않았습니다.
6. **무선 연결**: Data Output → Data Input(파일 경유), 플러그인의 송수신 컴포넌트 등은 와이어가 없어서 연결로 보지 않습니다.

### 키 해석

7. **`{n}h` / `{n}l`의 n은 반복 횟수가 아니라 입력/출력 번호**입니다. vim 습관대로 `3l`(세 칸)을 누르면 "출력 3을 받는 객체 없음"이 나옵니다.
8. **메시지가 두 경우를 구분하지 않습니다.** 입력 n이 아예 없는 경우와, 입력 n은 있지만 연결이 없는 경우 모두 "입력 n에 연결된 객체 없음"입니다.
9. [vim에서 더 가져올 것](vim-ideas.md)에서는 범위 `d2h`를 "상류 2단계"로 제안했습니다. 모션 `2h`(입력 2의 출처)와 같은 글자가 다른 뜻이 되므로, 연산자 + 범위 문법을 만들 때 함께 정리해야 합니다.

### 비주얼 모드에서 특히 드러나는 이유

비주얼 모드의 범위는 두 끝을 감싸는 **화면상 직사각형**인데, `h`/`l`은 **와이어 연결**을 따릅니다. 블록을 "왼쪽 열까지 넓히려고" `h`를 누르지만, 커서 객체의 부모가 없거나 부모가 다른 줄에 있으면 기대와 다르게 움직입니다. 정렬하지 않은 화면에서는 더 자주 어긋납니다. 지금은 화면 방향으로 움직이는 `Ctrl+hjkl`이 대안입니다.

### 해결 방향 후보 (정하지 않음)

- `h`/`l`이 실패하면 같은 방향의 **이웃 층(열)**으로 대신 이동: 이전/다음 층에서 세로 위치가 가장 가까운 객체. `j`/`k`가 층을 기준으로 움직이는 것과 대칭입니다. 비주얼 모드에서만 적용할지, 항상 적용할지도 정해야 합니다.
- 실패하면 `Ctrl+hjkl`처럼 화면상 가장 가까운 객체로 대신 이동.
- 8번 메시지를 "입력 n 없음"과 "입력 n에 연결 없음"으로 나누기.
- 7, 9번은 연산자 + 범위 문법을 설계할 때 `{n}`의 뜻을 함께 정하기.
- 고치기 전에 실제 정의 파일에서 1~4번이 각각 얼마나 되는지 세어 보기. 작업 폴더의 `sample.ghx`(커밋하지 않은 로컬 파일)를 쓸 수 있습니다.
