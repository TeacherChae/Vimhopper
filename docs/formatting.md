# 자동 정렬

> 실제 정의 파일로 비교한 결과 바꿀 점이 정리되어 있습니다: [자동 정렬 개선 조사](formatting-research.md).

구현: `src/Vimhopper.Core/CanvasLayout.cs` (공개 API, Relay 풀기, 덩어리 나누기), `LayeredLayout.cs` (계산), `WireGeometry.cs` (와이어 곡선), `src/Vimhopper.Engine/Formatter.cs` (문서에 적용). 키는 [키맵](keymap.md#정렬)을 참고하세요.

## 왜 필요한가

hjkl로 **와이어 연결을 따라** 이동하면, 화면 배치가 연결 구조와 어긋날 때 "지금 어디에 있고 다음에 어디로 가는지"를 눈으로 따라가기 어렵습니다. 키보드로 오가려면 연결 관계가 화면에서 명료하게 보이는 것이 무엇보다 중요합니다. 그리고 코드 포매터처럼, 사용자가 하나하나 손대지 않아도 알아서 깔끔해져야 합니다.

## 규칙

다음 순서로 계산합니다.

0. **Relay 풀기**: 풀 수 있는 Relay는 사용자가 넣은 것도 없애고 앞뒤를 직결합니다. Relay가 여러 출력을 받으면 받는 쪽에 그 순서대로 모두 잇습니다 (데이터를 그대로 넘기는 Relay이므로 결과가 같습니다). 데이터 연산(flatten 등)이 걸렸거나 입출력 한쪽이 비어 있는 Relay는 풀면 결과가 바뀌므로 일반 객체로 둡니다.
1. **층(열) 나누기**: 컴포넌트는 소스로부터의 최장 거리, 입력이 없는 객체(슬라이더, 패널 등)는 처음 쓰이는 객체 바로 앞 열 ([혼합 방안](#입력값의-위치-혼합-방안)). 순환이 있으면 화면상 오른쪽→왼쪽으로 가는 와이어를 뒤집어 끊습니다.
2. **가상 노드**: 두 열 이상 건너뛰는 와이어는 중간 열마다 Relay 크기의 가상 노드를 끼워 지나갈 자리를 확보합니다. 같은 출력에서 나가는 긴 와이어들은 가상 노드 줄기를 같이 쓰다가 받는 객체 바로 앞에서 갈라집니다.
3. **열 안 순서**: 기존 화면 위→아래 순서에서 시작해, 이웃 열 연결 대상의 평균 위치(barycenter)로 정렬하고 이웃한 두 객체를 바꿔보며 와이어 교차를 줄입니다. 교차가 줄지 않으면 기존 순서를 유지합니다.
4. **좌표**
   - 열 너비는 가장 넓은 객체 기준이고, 객체는 기본적으로 열 오른쪽에 맞춥니다 (출력 그립이 한 줄로 섬).
   - 열보다 좁은 객체와 가상 노드는 오른쪽·왼쪽 중 붙어 있는 와이어가 같은 열의 이웃을 덜 가로지르는 쪽에 붙입니다 (오른쪽에 붙이면 왼쪽 빈 자리로 들어오는 와이어가, 왼쪽에 붙이면 나가는 와이어가 꺾이면서 더 넓은 이웃 위를 지날 수 있으므로).
   - 세로 위치는 **맨 위 입력의 와이어 하나만 수평**이 되게 맞춥니다. 입력이 여러 개여도 중간에서 타협하지 않고, 나머지 와이어는 기울어집니다. 입력이 없는 객체는 맨 위 출력의 와이어를, 긴 와이어의 가상 노드는 출발 쪽을 기준으로 합니다.
   - 같은 열에서 자리가 겹치면 위쪽 객체가 자리를 갖고 아래쪽 객체가 밀려납니다.
5. **Relay 놓기**: Grasshopper는 와이어를 출력에서 입력까지 곡선 하나로 그리고 장애물을 피하지 않습니다. 그래서 **Relay 없이 그리면 객체를 가로지르는 곳에만** Relay를 놓습니다.
   - 줄기마다 출발점(또는 마지막 Relay)에서 Relay 없이 갈 수 있는 가장 먼 가상 노드까지 한 번에 가고, 그 사이에서 갈라지는 갈래도 모두 막히지 않을 때만 그렇게 합니다. 막히는 곳에서만 Relay를 두므로 경로마다 Relay가 최소에 가깝습니다.
   - 한 와이어에 Relay가 여러 개 들어갈 수 있고, 한 Relay에서 여러 갈래로 나갈 수 있습니다. 순환을 끊으려고 뒤집은 와이어에는 Relay를 놓지 않습니다.
   - 곡선 계산(`WireGeometry`): 양 끝에서 수평으로 출발하는 3차 베지어로, 제어점을 가로 거리의 0.5배만큼 뺀다고 근사합니다. 곡선이 가로·세로로 한 방향으로만 움직이므로, 상자의 왼쪽·오른쪽 가장자리에서의 곡선 높이만으로 겹침을 정확히 판정합니다. **0.5는 Rhino에서 실제 Grasshopper 와이어와 맞는지 확인이 필요합니다.** 객체와는 4px(`WireClearance`) 이상 떨어져 지나가야 통과로 봅니다.
   - 보장하는 것: 그려진 와이어는 **건너뛰는 열의 객체를 절대 가로지르지 않습니다.**
   - 보장하지 못하는 것: 와이어 양 끝 열의 이웃은 4번의 열 안 정렬로 줄일 뿐입니다 (열 안에는 Relay를 놓을 수 없고, 들어오는 쪽과 나가는 쪽이 모두 꺾이면 어느 쪽에 붙여도 한쪽이 이웃 위를 지납니다). 폭이 40~200으로 크게 다른 무작위 그래프에서 와이어의 약 4%입니다.

## 예시

```
w (슬라이더) ──→ w/2.A          열0         열1          열2          열3
'2' (패널)  ──→ w/2.B          [w  ]──┐
w/2 ──→ Neg ──→ Domain.A              ├──[ w/2 ]──┬──[Neg]────[Domain]
 └─────────────→ Domain.B      [ '2']─┘           └─────────────┘
```

- 층: `w/2`=1, `Neg`=2, `Domain`=3 (부모 `Neg`(2)와 `w/2`(1) 중 더 먼 쪽 + 1). 입력값 `w`, `'2'`는 `w/2` 바로 앞인 0열.
- `w/2 → Domain.B`는 2열을 건너뛰므로 2열에 가상 노드가 생기고, `Neg` 아래로 지나갑니다. 그대로 그린 곡선이 `Neg`를 가로지르면 그 자리에 Relay가 놓입니다.
- `Domain`은 맨 위 입력(A)의 와이어가 수평이 되도록 `Neg`에 맞춰지고, B 쪽 와이어는 기울어집니다.

## 멱등성

정렬된 결과를 다시 정렬해도 움직이지 않고 Relay도 그대로입니다. 이를 위해

- 가상 노드 자리는 실제 객체 순서만으로 정하고,
- 교차를 줄이는 탐색은 더 나아지지 않을 때까지 반복하고,
- Relay 판정은 정수 좌표로 반올림하기 전에 합니다 (반올림은 항상 같은 방향으로).
- 열 안 정렬·Relay 판정 모두 배치만으로 정해지는 결정적인 계산입니다.

계획이 문서의 현재 상태와 같으면 아무것도 바꾸지 않고 실행 취소 기록도 남기지 않습니다. 무작위 그래프로 테스트합니다.

## 실행 취소

객체 이동, Relay 추가·삭제, 와이어 변경을 실행 취소 기록 하나로 남깁니다. 기록 안의 동작 순서는 Relay 추가 → 와이어 → 기존 Relay 삭제 → 이동입니다. 실행 취소는 역순이므로 기존 Relay가 먼저 되살아난 뒤 와이어가 그것을 다시 가리키고, 다시 실행은 정순이므로 새 Relay가 먼저 생긴 뒤 와이어가 그것을 가리킵니다. **Rhino에서 확인이 필요합니다.**

## 결정 배경

### 입력값의 위치: 혼합 방안

최장 거리 규칙을 소스부터 셀지, 끝에서부터 거꾸로 셀지에 따라 결과가 크게 다릅니다.

- 소스부터 셈: 모든 입력값이 맨 왼쪽 0층으로 몰립니다. 위 예시의 Panel `'2'`도 0층에 가서, 실제로 쓰이는 곳이 멀면 와이어가 길게 늘어집니다.
- 끝에서부터 거꾸로 셈: 입력값이 쓰이는 컴포넌트 바로 앞 열에 놓입니다. 손으로 배치할 때(슬라이더를 쓰는 곳 근처에 둠)에 더 가깝습니다.
- **혼합 방안 (채택)**: 컴포넌트는 소스부터 세고, 입력값만 쓰이는 곳 바로 앞 열에 붙이기

### 층 나누는 규칙: 최장 거리

| 규칙 | w/2 | Neg | Construct Domain | 결과 |
|---|---|---|---|---|
| 최단 거리 (소스에서 몇 번 만에 닿나) | 0 | 1 | **1** | ❌ Neg와 같은 층이 되어 Neg → Domain 와이어가 같은 열 안에서 세로로 그어짐 |
| 최장 거리 (Sugiyama 기본) | 0 | 1 | **2** | ✅ 모든 부모보다 오른쪽에 놓여 와이어가 항상 왼쪽 → 오른쪽으로 흐름 |

### 남은 문제: 의미상 단계와 그래프 깊이가 어긋남

위 예시의 의미는 "Division | Construct Domain" 두 단계이고, Neg는 중간 계산을 돕는 보조 단계일 뿐입니다. 하지만 그래프 깊이로 보면 Neg도 한 열을 차지합니다. 검토할 대응 방안: Neg처럼 입력과 출력이 하나씩인 단순 변환 컴포넌트를 앞뒤 단계에 붙여서 "단계" 단위로 다루기, 그룹으로 단계 경계를 사용자가 직접 지정하기.

### 키

Grasshopper 기본 `Space`(컴포넌트 검색)를 건드리지 않기 위해 LazyVim식 리더 키(`<Space>cf`) 대신 vim 기본 문법을 따랐습니다. `==`(현재 덩어리)와 `g=`(전체)이고, `=`는 나중에 `=l`(하류만 정렬) 같은 연산자로 확장할 자리로 남겨둡니다.

### 조사한 기존 도구

기존 도구와 연동하지 않고 직접 구현했습니다. 아래는 결과 비교용으로 남겨둡니다.

| 도구 | 메모 |
|---|---|
| Grasshopper 기본 Align 위젯 | `Display > Canvas Widgets > Align`. 선택한 객체를 정렬·분배 |
| [AutoGraph](https://www.food4rhino.com/en/app/autograph) | 그래프 레이아웃 알고리즘으로 컴포넌트를 자동 배치하는 애드온. Rhino 4~6 시절 빌드라 Rhino 8 호환 확인 필요 |
| Bedrock | 오픈소스(MIT). 와이어 라우팅 스타일, 긴 와이어 흐리게 표시 등. 배치는 바꾸지 않음 |
| Graphviz / yEd | 외부 그래프 레이아웃 도구. 레이아웃 계산만 빌려 쓰는 방안 ([McNeel 포럼 논의](https://discourse.mcneel.com/t/automatically-group-grasshopper-components/218135)) |
| Bifocals, MetaHopper, SnappingGecko | 표시·정렬 관련 기능 확인 필요 |

### 아직 하지 않은 것: 보이는 방식만 바꾸기

배치는 그대로 두고, Vim 모드에서 선택 객체의 부모·자식 와이어를 강조하거나 `h`/`l`이 갈 대상을 미리 표시하는 방안입니다. [로드맵](roadmap.md)에 있습니다.
