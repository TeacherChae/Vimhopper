# 0020. 찾기: 덩어리→열→위아래 순서, `o{n}n`은 Invert, 입력줄에서만 IME 켜기

- 상태: 채택 (2026-11-10)
- 관련: [키맵 — 찾기](../keymap.md#찾기), `Search.cs`, `InputLine.cs`, `InputLineBox.cs`, `VimController.Search.cs`, [0002 키 후킹](0002-key-hook.md), [0009 덩어리](0009-islands.md)

## 맥락

vim의 `/` `n` `*`는 글의 순서(줄·열)를 따라갑니다. 캔버스에는 그런 순서가 없고, `n`은 이미 `o{n}` 뒤 Invert입니다. Vim 모드는 IME를 꺼서([0002](0002-key-hook.md)) 한글 별명을 칠 수 없습니다.

## 결정

- 맞는 것: NickName, Name, Category, SubCategory 중 하나에 대소문자 무시 부분 문자열. `*` / `#`는 ComponentGuid가 같은 것.
- 순서: 덩어리 순서(`{` `}`) → 층(정렬의 열) → 세로 가운데 → 왼쪽 끝. 정렬된 화면에서 덩어리마다 왼쪽 열부터 읽는 순서이고, `}`가 가는 첫 객체가 덩어리에서 처음 맞는 자리와 같은 규칙입니다.
- 끝에서 반대쪽 끝으로 돕니다 (vim의 `wrapscan`, 덩어리 이동과 다름). 커서 자신은 건너뜀.
- `*` / `#`도 마지막 찾기가 되어 `n`이 되풀이합니다 (`#`면 뒤로). vim과 같습니다.
- `o{n}` / `i{n}` 바로 뒤의 `n`은 Invert (기존 문법 우선). 그 밖의 `n`은 찾기.
- 입력줄(`/`, 4텀 `:`)은 키 대신 WM_CHAR를 받고, 열린 동안만 IME를 다시 붙입니다. 조합 글자는 IME 창 대신 HUD에 그립니다 (WM_IME_COMPOSITION을 직접 처리).
- 강조는 입력하는 동안만 (incsearch). 확정 뒤 남기는 `hlsearch`는 없습니다.

## 결과

- 정렬한 정의에서는 `n`이 화면을 위→아래로 훑습니다. 정렬하지 않은 화면에서는 층이 화면 위치와 어긋날 수 있습니다.
- 찾을 때마다 층을 계산합니다 (`}`와 같은 비용). `/` 입력 중에는 열 때 한 번만.
- IME 조합을 직접 처리하므로 IME마다 다를 수 있어 Rhino에서 확인해야 합니다 ([검증 목록](../verification.md)).
- 아직 없음: 연산자 + `/` 범위, `?`, 찾기 기록.

## 버린 대안

| 대안 | 버린 이유 |
|---|---|
| 화면 위치 순서 (위→아래, 왼쪽→오른쪽) | 같은 덩어리 안에서도 흐름과 무관하게 섞임. `gyy`의 X→Y 순서도 같은 문제 |
| `o{n}` 뒤에서도 `n`은 찾기, Invert를 다른 키로 | 기존 `o0n` 습관이 깨짐 |
| 입력줄에서 IME 없이 영문만 | 한글 별명이 흔함 |
| IME 기본 조합 창 그대로 | 창이 캔버스 왼쪽 위 등 엉뚱한 곳에 뜸 |
