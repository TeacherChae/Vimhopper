# Vimhopper

Grasshopper 캔버스를 nvim처럼 키보드만으로 다루는 플러그인입니다. hjkl로 컴포넌트를 순회하고, `o{n}` → `i{n}`으로 와이어를 연결하며, 연결하면서 flatten / graft 같은 데이터 연산을 바로 붙일 수 있습니다.

> 상태: 초기 프로토타입 (v0.1.0) · 대상: Rhino 8 (.NET 7) · Grasshopper 1

## 키맵 (초안)

### 모드

- **Normal 모드**: Grasshopper 기본 상태. 마우스로 조작합니다.
- **Vim 모드**: 키보드로 조작합니다. 화면 좌하단에 `-- VIM --`이 표시됩니다.

| 키 | 동작 |
|---|---|
| `Esc` (Normal 모드에서) | Vim 모드 진입 |
| `a` | Vim 모드 종료 (Normal 모드로) |
| `Esc` (Vim 모드에서) | 입력 중인 명령·고른 소스 취소 |

Vim 모드에서는 캔버스의 한글 IME가 자동으로 꺼지고 모드를 나가면 복구됩니다. 아래 표에 있는 `Ctrl` 조합을 제외한 `Ctrl`/`Alt` 조합(`Ctrl+S`, `Ctrl+Z` 등)과 `Delete`, 방향키, PageUp/PageDown, F키는 Grasshopper가 그대로 처리합니다.

### 이동

`hjkl`은 화면 위치가 아니라 **와이어 연결**을 따라 움직입니다.

| 키 | 동작 |
|---|---|
| `l` | 자식으로: 이 객체의 출력을 받는 객체 중 맨 위 |
| `h` | 부모로: 이 객체의 입력에 연결된 객체 중 맨 위. `l`로 왔다면 왔던 객체로 정확히 돌아감 |
| `j` / `k` | 형제 사이 아래 / 위. `l`로 왔으면 같은 부모의 자식들, `h`로 왔으면 같은 자식의 부모들 |
| `Ctrl+h` `Ctrl+j` `Ctrl+k` `Ctrl+l` | 연결과 무관하게 화면상 좌 / 하 / 상 / 우로 가장 가까운 객체 (연결 없는 객체로 갈 때) |

형제 순서는 화면상 위→아래입니다. 이동 기록 없이 `j`/`k`를 누르면 맨 위 부모의 자식들 사이를, 부모가 없는 시작 객체(슬라이더 등)에서는 같은 자식에 연결된 부모들 사이를 이동합니다.

> ⚠️ 위 표는 **현재 구현된 동작**입니다. 이동 기록에 따라 결과가 달라져서 예측하기 어렵다는 문제가 있어 기준을 다시 정하는 중입니다. 아래 [설계 메모: hjkl 기준](#설계-메모-hjkl-기준-논의-중)을 참고하세요.

### 화면

| 키 | 동작 |
|---|---|
| `Ctrl+=` / `Ctrl+-` | 확대 / 축소 (Grasshopper 기본 PageUp / PageDown과 같음) |
| `z` | 선택된 객체를 화면 중앙으로 |

선택이 바뀌어도 화면은 객체가 가장자리 여백 밖으로 나갈 때만 필요한 만큼 움직입니다 (vim의 `scrolloff`).

### 정렬

| 키 | 동작 |
|---|---|
| `==` | 선택 객체와 와이어로 이어진 덩어리만 자동 정렬 (vim의 `==`가 현재 줄만 정렬하듯) |
| `g=` | 문서 전체 자동 정렬. 덩어리마다 따로 정렬하고 서로 겹치면 아래로 밂 |

- 와이어 흐름에 따라 왼쪽→오른쪽 열로 나누고, 교차가 줄도록 열 안 순서를 정하고, 맨 위 입력의 와이어가 수평이 되도록 높이를 맞춥니다. 자세한 규칙은 아래 [자동 정렬 규칙](#자동-정렬-규칙)을 참고하세요.
- 덩어리의 왼쪽 위 모서리는 제자리에 남습니다. 이미 정렬된 배치를 다시 정렬해도 움직이지 않습니다.
- **Relay를 알아서 넣고 뺍니다.** 범위 안의 Relay는 사용자가 넣은 것도 모두 풀었다가, **Relay가 없으면 와이어가 다른 객체를 가로지르는 곳에만** 다시 놓습니다. 꺾이더라도 사이에 아무것도 없으면 곡선 그대로 둡니다. 데이터 연산(flatten 등)이 걸렸거나 입출력 한쪽이 비어 있는 Relay는 풀지 않고 그대로 둡니다.
- 객체 이동, Relay 추가·삭제, 와이어 변경을 `u`(또는 `Ctrl+Z`) 한 번으로 되돌립니다.
- `==`는 덩어리 밖 객체를 옮기지 않으므로, 덩어리가 커지면 주변 객체와 겹칠 수 있습니다.
- Grasshopper 기본 `Space`(컴포넌트 검색)와 겹치지 않도록 리더 키는 쓰지 않습니다.

### 연결

| 키 | 동작 |
|---|---|
| `o{n}` | 선택된 객체의 출력[n]을 소스로 고름 (주황색 원으로 표시) |
| `i{n}` | 고른 소스를 선택된 객체의 입력[n]에 연결, 기존 와이어는 교체 |
| `I{n}` | 기존 와이어를 유지하고 추가로 연결 (Shift+드래그와 같음) |
| `u` | 실행 취소 |

- 인덱스는 **0부터** 시작합니다. Vim 모드에서는 선택된 객체의 입출력 옆에 번호가 표시됩니다.
- 파라미터가 10개 이하면 한 자리 숫자를 누르는 즉시 확정됩니다. 11개 이상이면 숫자를 더 붙일 수 없을 때 확정되고, 그 전에는 다음 키나 `Enter`로 확정합니다. 예를 들어 출력이 15개이면 `o2`는 즉시 확정, `o1`은 `o12`가 될 수 있으므로 다음 키를 기다립니다.
- 소스는 연결 후 해제됩니다.

### 데이터 연산자

`o{n}` 또는 `i{n}` 바로 뒤에 붙이면 방금 고른 파라미터에 적용되고 여러 개를 이어 붙일 수 있습니다. 같은 연산자를 다시 적용하면 꺼집니다.

| 키 | 연산 |
|---|---|
| `f` | Flatten |
| `g` | Graft |
| `s` | Simplify |
| `r` | Reverse |
| `n` | Invert (Boolean 파라미터만) |

### 예시

```
o0f  Ctrl+l Ctrl+l  i1   출력[0]을 flatten하고, 화면 오른쪽으로 두 칸 가서 입력[1]에 연결
o2   lj  I0g     출력[2]를 고르고, 자식의 다음 형제로 가서 입력[0]에 추가 연결한 뒤 그 입력을 graft
```

## 구조

```
src/Vimhopper.Core     Grasshopper 비의존 로직 (KeyParser 상태 머신, 연결 따라 이동, 화면 방향 이동, 자동 정렬 CanvasLayout) — netstandard2.0
src/Vimhopper.Engine   실제 플러그인 로직 — 키 후킹, 명령 실행, 오버레이 그리기
src/Vimhopper          얇은 로더 (.gha) — 엔진을 불러와 캔버스에 붙이고, Debug 빌드에서는 핫 리로드
tests/                 Vimhopper.Core 단위 테스트 (xUnit)
scripts/link-dev.ps1   개발용 .ghlink 생성
scripts/watch.ps1      저장할 때마다 엔진 자동 빌드
```

키 입력은 캔버스 HWND를 서브클래싱(`NativeWindow`)해서 Grasshopper보다 먼저 받습니다.

## 개발

```powershell
scripts\link-dev.ps1      # 최초 1회: Grasshopper가 빌드 폴더를 직접 로드하도록 연결
dotnet build              # 전체 빌드 → src/Vimhopper/bin/Debug/net7.0-windows/
dotnet test
```

### 핫 리로드

Debug 빌드의 로더는 엔진(`Vimhopper.Engine.dll`, `Vimhopper.Core.dll`)을 임시 폴더로 복사해서 언로드 가능한 `AssemblyLoadContext`에 올립니다. 원본 dll이 잠기지 않으므로 **Rhino를 켜둔 채 빌드할 수 있고**, 빌드 폴더의 dll이 바뀌면 이전 엔진을 떼어내고 새 엔진으로 바꿉니다. Vim 모드 여부와 선택 객체는 리로드 후에도 유지되고, Rhino 명령창에 `Vimhopper: engine reloaded`가 표시됩니다.

```powershell
scripts\watch.ps1         # 파일을 저장하면 자동 빌드 → Rhino에 자동 반영
```

- **재시작이 필요한 경우**: 로더(`src/Vimhopper`)를 고쳤을 때. 이때는 Rhino를 닫고 `dotnet build` 합니다.
- 엔진의 `VimController`는 캔버스에 연결한 이벤트를 모두 `Dispose`에서 해제해야 합니다. 빠뜨리면 이전 버전이 계속 키를 받습니다.
- Release 빌드는 핫 리로드 없이 엔진을 일반 방식으로 로드합니다.

## 설계 메모: hjkl 기준 (논의 중)

### 문제

Grasshopper의 연결은 트리가 아니라 방향 그래프(DAG)입니다. 한 컴포넌트가 **부모도 여러 개, 자식도 여러 개** 가질 수 있습니다. 지금 구현(`TreeNavigator`)은 "어느 방향으로 건너왔는가"라는 이동 기록으로 이 모호함을 풀고 있습니다.

- `h`: `l`로 왔으면 왔던 부모로 돌아가고, 아니면 맨 위 부모로 갑니다.
- `j`/`k`: `l`로 왔으면 같은 부모의 자식들 사이를, `h`로 왔으면 같은 자식의 부모들 사이를 오갑니다.

그런데 이렇게 하면 **같은 컴포넌트에서 같은 키를 눌러도 직전 경로에 따라 결과가 달라집니다.** 예측하기 어렵습니다.

### 정한 것

이동 기록과 무관하게 **현재 선택된 컴포넌트만 보고** 결정합니다.

- **`h` = 부모 중 첫 번째**
- **`l` = 자식 중 첫 번째**

### 아직 정할 것

**1. "첫 번째"의 순서 기준**
- (a) 화면상 위→아래 (현재 구현). 눈에 보이는 순서와 같지만, 컴포넌트를 옮기면 순서가 바뀝니다.
- (b) 파라미터 인덱스 순서. 부모는 입력[0]의 소스부터, 자식은 출력[0]의 수신자부터 셉니다. `o{n}`/`i{n}`의 번호 체계와 일관되고 레이아웃과 무관하지만, 한 파라미터에 여러 개가 연결된 경우의 순서를 또 정해야 합니다.

**2. `j`/`k`의 의미** (후보)
- (A) **첫 번째 부모의 자식들 사이** (형제). 이동 기록 없이 결정되고 "같은 위계"라는 처음 의도에 가깝습니다. 다만 부모가 없는 객체(슬라이더 등)에서는 정의되지 않고, 부모가 여럿이면 첫 번째 부모 외의 형제로는 갈 수 없습니다.
- (B) **`h`/`l`이 갈 대상을 고르는 키**. `j`/`k`로 "다음에 `h`(또는 `l`)를 누르면 몇 번째 부모(자식)로 갈지"를 바꾸고, 선택된 후보를 화면에 표시합니다. 객체는 움직이지 않습니다. 부모·자식이 여러 개인 경우를 모두 다룰 수 있지만, 키 한 번으로 이동하지 않습니다.
- (C) **위상 깊이(소스로부터의 거리)가 같은 객체들 사이**. 그래프를 층으로 나눠 같은 층 안에서 위아래로 움직입니다. 직관적일 수 있지만, 층 계산이 레이아웃과 어긋나는 경우가 생깁니다.
- (D) **화면상 위·아래 이동** (지금의 `Ctrl+j`/`Ctrl+k`와 같음). 가장 단순하지만, 연결 기반이라는 hjkl의 일관성이 깨집니다.

**3. 되돌아가기**
`h`가 항상 첫 번째 부모로 가면 `l` → `h`가 제자리로 돌아온다는 보장이 없습니다. A에서 `l`로 자식 B에 갔는데 B의 첫 번째 부모가 A가 아니면, `h`는 다른 부모로 갑니다. vim의 `Ctrl+o`/`Ctrl+i`처럼 **별도의 이동 기록 키**를 두는 방안을 검토 중입니다.

## 설계 메모: 캔버스 포매팅 (아이디어)

### 왜 필요한가

hjkl로 **와이어 연결을 따라** 이동하면, 화면 배치가 연결 구조와 어긋날 때 "지금 어디에 있고 다음에 어디로 가는지"를 눈으로 따라가기 어렵습니다. 키보드로 오가려면 연결 관계가 화면에서 명료하게 보이는 것이 무엇보다 중요합니다.

### 방향 후보

**1. 자동 정렬 (레이아웃 자체를 바꾸기)**
- **층 기반 레이아웃** (Sugiyama 방식): 소스에서 멀어질수록 오른쪽 열로 보내고, 열 안에서는 와이어 교차가 줄도록 위아래 순서를 정합니다.
  - hjkl 기준과 잘 맞습니다. `h`/`l` = 열 사이 이동, `j`/`k` = 같은 열 안 이동이 되므로, 위 설계 메모의 `j`/`k` 후보 (C) 위상 깊이와 자연스럽게 이어집니다.
  - 층 나누는 규칙과 남는 문제는 아래 [층 기반 레이아웃 검토](#층-기반-레이아웃-검토)를 참고하세요.
- 범위를 고를 수 있어야 합니다: 전체 문서 / 선택 영역 / 그룹 단위
- 사용자가 직접 잡은 배치를 망가뜨리지 않아야 합니다: 실행 취소, 고정 핀 같은 장치

**2. 보이는 방식만 바꾸기 (배치는 그대로)**
- Vim 모드에서 **선택된 컴포넌트의 부모·자식 와이어를 강조**하고 나머지는 흐리게 표시
- `h`/`l`을 누르면 갈 대상(첫 번째 부모·자식)과 `j`/`k` 후보를 미리 표시
- 화면 밖에 있는 연결 대상을 가장자리에 화살표로 표시

### 층 기반 레이아웃 검토

예제: `panel_dividing.ghx`의 반폭 도메인 구성 부분

```
w/2 (Division) ──→ Neg ──→ -w/2..w/2 (Construct Domain).A
      └────────────────────→ -w/2..w/2.B
```

손으로 배치한 x 좌표는 `w/2` 1432 → `Neg` 1563 → `-w/2..w/2` 1723으로, 이미 3열입니다.

**1. 층 나누는 규칙: 최장 거리를 써야 합니다**

| 규칙 | w/2 | Neg | Construct Domain | 결과 |
|---|---|---|---|---|
| 최단 거리 (소스에서 몇 번 만에 닿나) | 0 | 1 | **1** | ❌ Neg와 같은 층이 되어 Neg → Domain 와이어가 같은 열 안에서 세로로 그어짐 |
| 최장 거리 (Sugiyama 기본) | 0 | 1 | **2** | ✅ 모든 부모보다 오른쪽에 놓여 와이어가 항상 왼쪽 → 오른쪽으로 흐름 |

최장 거리 규칙에서 `w/2 → Domain.B`처럼 두 층 이상 건너뛰는 와이어는, 중간 층에 보이지 않는 가상 노드를 끼워서 지나갈 자리를 확보합니다. 그래야 와이어가 다른 컴포넌트를 가로지르지 않습니다.

**2. 남는 문제: 의미상 단계와 그래프 깊이가 어긋남**

이 부분의 의미는 "Division | Construct Domain" 두 단계이고, Neg는 중간 계산을 돕는 보조 단계일 뿐입니다. 하지만 그래프 깊이로 보면 Neg도 한 열을 차지합니다.

- `j`/`k` 후보 (C) "같은 층": Neg 층에는 Neg 하나뿐이라, 의미상 같은 단계라는 느낌과 실제 층이 맞지 않습니다.
- `l` = 첫 번째 자식: `w/2`의 자식은 Neg와 Domain 둘입니다. 화면 위→아래로 세면 Neg가 먼저이고, 파라미터 순서로 세면 출력 R에 연결된 순서에 따라 달라집니다.
- `h` = 첫 번째 부모: Domain의 부모는 입력 A 쪽 Neg와 입력 B 쪽 `w/2`입니다. 파라미터 순서로 세면 Neg로 가고, `w/2`로 바로 돌아가지 못합니다.
- 검토할 대응 방안: Neg처럼 입력과 출력이 하나씩인 단순 변환 컴포넌트를 앞뒤 단계에 붙여서 "단계" 단위로 다루기, 그룹으로 단계 경계를 사용자가 직접 지정하기

**3. 슬라이더·패널 등 입력값의 위치 → 혼합 방안으로 결정**

최장 거리 규칙을 소스부터 셀지, 끝에서부터 거꾸로 셀지에 따라 결과가 크게 다릅니다.

- 소스부터 셈: 모든 입력값이 맨 왼쪽 0층으로 몰립니다. `w/2.B`에 들어가는 Panel `'2'`도 0층에 가서, 실제로 쓰이는 곳까지 와이어가 길게 늘어집니다.
- 끝에서부터 거꾸로 셈: 입력값이 쓰이는 컴포넌트 바로 앞 열에 놓입니다. 손으로 배치할 때(슬라이더를 쓰는 곳 근처에 둠)에 더 가깝습니다.
- **혼합 방안 (채택)**: 컴포넌트는 소스부터 세고, 입력값만 쓰이는 곳 바로 앞 열에 붙이기

기존 도구와 연동하지 않고 Vimhopper에 직접 구현했습니다 (`CanvasLayout`). 위 도구 조사는 결과 비교용으로 남겨둡니다.

### 자동 정렬 규칙

`src/Vimhopper.Core/CanvasLayout.cs` (공개 API, Relay 풀기, 덩어리 나누기), `LayeredLayout.cs` (계산). 다음 순서로 계산합니다.

0. **Relay 풀기**: 풀 수 있는 Relay를 없애고 앞뒤를 직결합니다. Relay가 여러 출력을 받으면 받는 쪽에 그 순서대로 모두 잇습니다 (데이터를 그대로 넘기는 Relay이므로 결과가 같습니다).
1. **층(열) 나누기**: 컴포넌트는 소스로부터의 최장 거리, 입력이 없는 객체는 처음 쓰이는 객체 바로 앞 열 (위 3번의 혼합 방안). 순환이 있으면 화면상 오른쪽→왼쪽으로 가는 와이어를 뒤집어 끊습니다.
2. **가상 노드**: 두 열 이상 건너뛰는 와이어는 중간 열마다 Relay 크기의 가상 노드를 끼워 지나갈 자리를 확보합니다. 같은 출력에서 나가는 긴 와이어들은 가상 노드 줄기를 같이 쓰다가 받는 객체 바로 앞에서 갈라집니다.
3. **열 안 순서**: 기존 화면 위→아래 순서에서 시작해, 이웃 열 연결 대상의 평균 위치(barycenter)로 정렬하고 이웃한 두 객체를 바꿔보며 와이어 교차를 줄입니다. 교차가 줄지 않으면 기존 순서를 유지합니다.
4. **좌표**: 열 너비는 가장 넓은 객체 기준이고 객체는 기본적으로 열 오른쪽에 맞춥니다(출력 그립이 한 줄로 섬). 단, 열보다 좁은 객체와 가상 노드는 오른쪽·왼쪽 중 붙어 있는 와이어가 같은 열의 이웃을 덜 가로지르는 쪽에 붙입니다 (오른쪽에 붙이면 왼쪽 빈 자리로 들어오는 와이어가, 왼쪽에 붙이면 나가는 와이어가 꺾이면서 더 넓은 이웃 위를 지날 수 있으므로). 세로 위치는 **맨 위 입력의 와이어 하나만 수평**이 되게 맞춥니다. 입력이 여러 개여도 중간에서 타협하지 않고, 나머지 와이어는 기울어집니다. 입력이 없는 객체(슬라이더 등)는 맨 위 출력의 와이어를, 긴 와이어의 가상 노드는 출발 쪽을 기준으로 합니다. 같은 열에서 자리가 겹치면 위쪽 객체가 자리를 갖고 아래쪽 객체가 밀려납니다.
5. **Relay 놓기**: Grasshopper는 와이어를 출력에서 입력까지 곡선 하나로 그리고 장애물을 피하지 않습니다. 그래서 **Relay 없이 그리면 객체를 가로지르는 곳에만** Relay를 놓습니다. 줄기마다 출발점(또는 마지막 Relay)에서 Relay 없이 갈 수 있는 가장 먼 가상 노드까지 한 번에 가고, 그 사이에서 갈라지는 갈래도 모두 막히지 않을 때만 그렇게 합니다. 막히는 곳에서만 Relay를 두므로 경로마다 Relay가 최소에 가깝습니다. 한 와이어에 Relay가 여러 개 들어갈 수 있고, 한 Relay에서 여러 갈래로 나갈 수 있습니다. 순환을 끊으려고 뒤집은 와이어에는 Relay를 놓지 않습니다.
   - 곡선 계산은 `WireGeometry`: 양 끝에서 수평으로 출발하는 3차 베지어로, 제어점을 가로 거리의 0.5배만큼 뺀다고 근사합니다. 곡선이 가로·세로로 한 방향으로만 움직이므로, 상자의 왼쪽·오른쪽 가장자리에서의 곡선 높이만으로 겹침을 정확히 판정합니다. **0.5는 Rhino에서 실제 Grasshopper 와이어와 맞는지 확인이 필요합니다.** 객체와는 4px(`WireClearance`) 이상 떨어져 지나가야 통과로 봅니다.
   - 보장하는 것: 그려진 와이어는 **건너뛰는 열의 객체를 절대 가로지르지 않습니다.** 보장하지 못하는 것: 와이어 양 끝 열의 이웃은 4번의 열 안 정렬로 줄일 뿐입니다 (열 안에는 Relay를 놓을 수 없고, 들어오는 쪽과 나가는 쪽이 모두 꺾이면 어느 쪽에 붙여도 한쪽이 이웃 위를 지납니다). 폭이 40~200으로 크게 다른 무작위 그래프에서 와이어의 약 4%입니다.

**멱등성**: 정렬된 결과를 다시 정렬해도 움직이지 않고 Relay도 그대로입니다. 이를 위해 (a) 가상 노드 자리는 실제 객체 순서만으로 정하고, (b) 교차를 줄이는 탐색은 더 나아지지 않을 때까지 반복하고, (c) Relay 판정은 정수 좌표로 반올림하기 전에 하고, 열 안 정렬·Relay 판정 모두 배치만으로 정해지는 결정적인 계산입니다. 계획이 문서의 현재 상태와 같으면 아무것도 바꾸지 않고 실행 취소 기록도 남기지 않습니다. 무작위 그래프로 테스트합니다.

hjkl은 Relay도 일반 객체처럼 순회합니다 (Relay마다 여러 갈래로 나갈 수 있으므로 건너뛰지 않음).
