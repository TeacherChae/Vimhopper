# Vimhopper

Grasshopper 캔버스를 nvim처럼 키보드만으로 다루는 플러그인입니다. hjkl로 컴포넌트를 순회하고, `o{n}` → `i{n}`으로 와이어를 연결하며, 연결하면서 flatten / graft 같은 데이터 연산을 바로 붙일 수 있습니다.

> 상태: 초기 프로토타입 (v0.1.0) · 대상: Rhino 8 (.NET 7) · Grasshopper 1

## 키맵 (초안)

### 모드

- **Normal 모드**: Grasshopper 기본 상태. 마우스로 조작합니다.
- **Vim 모드**: 키보드로 조작합니다. 화면 좌하단에 `-- VIM --`이 표시됩니다.

| 키 | 동작 |
|---|---|
| `Esc` (Normal 모드에서) | Vim 모드 진입 |
| `a` | Vim 모드 종료 (Normal 모드로) |
| `Esc` (Vim 모드에서) | 입력 중인 명령·고른 소스 취소 |

Vim 모드에서는 캔버스의 한글 IME가 자동으로 꺼지고 모드를 나가면 복구됩니다. 아래 표에 있는 `Ctrl` 조합을 제외한 `Ctrl`/`Alt` 조합(`Ctrl+S`, `Ctrl+Z` 등)과 `Delete`, 방향키, PageUp/PageDown, F키는 Grasshopper가 그대로 처리합니다.

### 이동

`hjkl`은 화면 위치가 아니라 **와이어 연결**을 따라 움직입니다.

| 키 | 동작 |
|---|---|
| `l` | 자식으로: 이 객체의 출력을 받는 객체 중 맨 위 |
| `h` | 부모로: 이 객체의 입력에 연결된 객체 중 맨 위. `l`로 왔다면 왔던 객체로 정확히 돌아감 |
| `j` / `k` | 형제 사이 아래 / 위. `l`로 왔으면 같은 부모의 자식들, `h`로 왔으면 같은 자식의 부모들 |
| `Ctrl+h` `Ctrl+j` `Ctrl+k` `Ctrl+l` | 연결과 무관하게 화면상 좌 / 하 / 상 / 우로 가장 가까운 객체 (연결 없는 객체로 갈 때) |

형제 순서는 화면상 위→아래입니다. 이동 기록 없이 `j`/`k`를 누르면 맨 위 부모의 자식들 사이를, 부모가 없는 시작 객체(슬라이더 등)에서는 같은 자식에 연결된 부모들 사이를 이동합니다.

> ⚠️ 위 표는 **현재 구현된 동작**입니다. 이동 기록에 따라 결과가 달라져서 예측하기 어렵다는 문제가 있어 기준을 다시 정하는 중입니다. 아래 [설계 메모: hjkl 기준](#설계-메모-hjkl-기준-논의-중)을 참고하세요.

### 화면

| 키 | 동작 |
|---|---|
| `Ctrl+=` / `Ctrl+-` | 확대 / 축소 (Grasshopper 기본 PageUp / PageDown과 같음) |
| `z` | 선택된 객체를 화면 중앙으로 |

선택이 바뀌어도 화면은 객체가 가장자리 여백 밖으로 나갈 때만 필요한 만큼 움직입니다 (vim의 `scrolloff`).

### 연결

| 키 | 동작 |
|---|---|
| `o{n}` | 선택된 객체의 출력[n]을 소스로 고름 (주황색 원으로 표시) |
| `i{n}` | 고른 소스를 선택된 객체의 입력[n]에 연결, 기존 와이어는 교체 |
| `I{n}` | 기존 와이어를 유지하고 추가로 연결 (Shift+드래그와 같음) |
| `u` | 실행 취소 |

- 인덱스는 **0부터** 시작합니다. Vim 모드에서는 선택된 객체의 입출력 옆에 번호가 표시됩니다.
- 파라미터가 10개 이하면 한 자리 숫자를 누르는 즉시 확정됩니다. 11개 이상이면 숫자를 더 붙일 수 없을 때 확정되고, 그 전에는 다음 키나 `Enter`로 확정합니다. 예를 들어 출력이 15개이면 `o2`는 즉시 확정, `o1`은 `o12`가 될 수 있으므로 다음 키를 기다립니다.
- 소스는 연결 후 해제됩니다.

### 데이터 연산자

`o{n}` 또는 `i{n}` 바로 뒤에 붙이면 방금 고른 파라미터에 적용되고 여러 개를 이어 붙일 수 있습니다. 같은 연산자를 다시 적용하면 꺼집니다.

| 키 | 연산 |
|---|---|
| `f` | Flatten |
| `g` | Graft |
| `s` | Simplify |
| `r` | Reverse |
| `n` | Invert (Boolean 파라미터만) |

### 예시

```
o0f  Ctrl+l Ctrl+l  i1   출력[0]을 flatten하고, 화면 오른쪽으로 두 칸 가서 입력[1]에 연결
o2   lj  I0g     출력[2]를 고르고, 자식의 다음 형제로 가서 입력[0]에 추가 연결한 뒤 그 입력을 graft
```

## 구조

```
src/Vimhopper.Core     Grasshopper 비의존 로직 (KeyParser 상태 머신, 연결 따라 이동, 화면 방향 이동) — netstandard2.0
src/Vimhopper.Engine   실제 플러그인 로직 — 키 후킹, 명령 실행, 오버레이 그리기
src/Vimhopper          얇은 로더 (.gha) — 엔진을 불러와 캔버스에 붙이고, Debug 빌드에서는 핫 리로드
tests/                 Vimhopper.Core 단위 테스트 (xUnit)
scripts/link-dev.ps1   개발용 .ghlink 생성
scripts/watch.ps1      저장할 때마다 엔진 자동 빌드
```

키 입력은 캔버스 HWND를 서브클래싱(`NativeWindow`)해서 Grasshopper보다 먼저 받습니다.

## 개발

```powershell
scripts\link-dev.ps1      # 최초 1회: Grasshopper가 빌드 폴더를 직접 로드하도록 연결
dotnet build              # 전체 빌드 → src/Vimhopper/bin/Debug/net7.0-windows/
dotnet test
```

### 핫 리로드

Debug 빌드의 로더는 엔진(`Vimhopper.Engine.dll`, `Vimhopper.Core.dll`)을 임시 폴더로 복사해서 언로드 가능한 `AssemblyLoadContext`에 올립니다. 원본 dll이 잠기지 않으므로 **Rhino를 켜둔 채 빌드할 수 있고**, 빌드 폴더의 dll이 바뀌면 이전 엔진을 떼어내고 새 엔진으로 바꿉니다. Vim 모드 여부와 선택 객체는 리로드 후에도 유지되고, Rhino 명령창에 `Vimhopper: engine reloaded`가 표시됩니다.

```powershell
scripts\watch.ps1         # 파일을 저장하면 자동 빌드 → Rhino에 자동 반영
```

- **재시작이 필요한 경우**: 로더(`src/Vimhopper`)를 고쳤을 때. 이때는 Rhino를 닫고 `dotnet build` 합니다.
- 엔진의 `VimController`는 캔버스에 연결한 이벤트를 모두 `Dispose`에서 해제해야 합니다. 빠뜨리면 이전 버전이 계속 키를 받습니다.
- Release 빌드는 핫 리로드 없이 엔진을 일반 방식으로 로드합니다.

## 설계 메모: hjkl 기준 (논의 중)

### 문제

Grasshopper의 연결은 트리가 아니라 방향 그래프(DAG)입니다. 한 컴포넌트가 **부모도 여러 개, 자식도 여러 개** 가질 수 있습니다. 지금 구현(`TreeNavigator`)은 "어느 방향으로 건너왔는가"라는 이동 기록으로 이 모호함을 풀고 있습니다.

- `h`: `l`로 왔으면 왔던 부모로 돌아가고, 아니면 맨 위 부모로 갑니다.
- `j`/`k`: `l`로 왔으면 같은 부모의 자식들 사이를, `h`로 왔으면 같은 자식의 부모들 사이를 오갑니다.

그런데 이렇게 하면 **같은 컴포넌트에서 같은 키를 눌러도 직전 경로에 따라 결과가 달라집니다.** 예측하기 어렵습니다.

### 정한 것

이동 기록과 무관하게 **현재 선택된 컴포넌트만 보고** 결정합니다.

- **`h` = 부모 중 첫 번째**
- **`l` = 자식 중 첫 번째**

### 아직 정할 것

**1. "첫 번째"의 순서 기준**
- (a) 화면상 위→아래 (현재 구현). 눈에 보이는 순서와 같지만, 컴포넌트를 옮기면 순서가 바뀝니다.
- (b) 파라미터 인덱스 순서. 부모는 입력[0]의 소스부터, 자식은 출력[0]의 수신자부터 셉니다. `o{n}`/`i{n}`의 번호 체계와 일관되고 레이아웃과 무관하지만, 한 파라미터에 여러 개가 연결된 경우의 순서를 또 정해야 합니다.

**2. `j`/`k`의 의미** (후보)
- (A) **첫 번째 부모의 자식들 사이** (형제). 이동 기록 없이 결정되고 "같은 위계"라는 처음 의도에 가깝습니다. 다만 부모가 없는 객체(슬라이더 등)에서는 정의되지 않고, 부모가 여럿이면 첫 번째 부모 외의 형제로는 갈 수 없습니다.
- (B) **`h`/`l`이 갈 대상을 고르는 키**. `j`/`k`로 "다음에 `h`(또는 `l`)를 누르면 몇 번째 부모(자식)로 갈지"를 바꾸고, 선택된 후보를 화면에 표시합니다. 객체는 움직이지 않습니다. 부모·자식이 여러 개인 경우를 모두 다룰 수 있지만, 키 한 번으로 이동하지 않습니다.
- (C) **위상 깊이(소스로부터의 거리)가 같은 객체들 사이**. 그래프를 층으로 나눠 같은 층 안에서 위아래로 움직입니다. 직관적일 수 있지만, 층 계산이 레이아웃과 어긋나는 경우가 생깁니다.
- (D) **화면상 위·아래 이동** (지금의 `Ctrl+j`/`Ctrl+k`와 같음). 가장 단순하지만, 연결 기반이라는 hjkl의 일관성이 깨집니다.

**3. 되돌아가기**
`h`가 항상 첫 번째 부모로 가면 `l` → `h`가 제자리로 돌아온다는 보장이 없습니다. A에서 `l`로 자식 B에 갔는데 B의 첫 번째 부모가 A가 아니면, `h`는 다른 부모로 갑니다. vim의 `Ctrl+o`/`Ctrl+i`처럼 **별도의 이동 기록 키**를 두는 방안을 검토 중입니다.
